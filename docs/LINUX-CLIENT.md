# Linux 官方客户端：代理、证书与登录持久化

本指南记录官方 Grok Bot `0.66.0` 在受管理 Linux 桌面中的一次诊断与验收（2026-10-06），用于定位“网页已登录、应用无法连接”及“应用重开后需要重新登录”。它不安装 PLUS、不修改官方安装包，也不认证 PLUS 的消息路由或 DeepSeek 往返。公开构建的支持范围见[兼容性与证据等级](COMPATIBILITY.md)。

## 先分清故障层

| 现象 | 优先检查 | 不能据此得出的结论 |
| --- | --- | --- |
| 浏览器登录成功，但 `sand://` 被策略拦截 | 保持客户端打开，手动切回应用；检查应用是否取得登录状态 | 自定义协议拦截不等于认证失败或后台网络故障 |
| 已登录，但提示连接困难、列表加载失败 | 实际应用请求是否采用既有代理，以及证书错误类型 | 浏览器、curl 或终端 Node 的 HTTP 200 不证明应用 RPC 可用 |
| 正常退出重开后需要登录 | 同一用户和 profile、会话密钥服务、所选存储后端是否可用 | 单独看到凭据文件缺失，不足以证明凭据被删除 |
| 客户端列表已恢复 | 再做同 profile 的正常退出与重开验收 | 不证明 PLUS 路由、供应商模型、例行任务或所有员工业务正常 |

官方[登录故障排查](https://docs.x.ai/grok-bot/troubleshooting)支持网页登录完成后手动返回客户端。不要通过更换浏览器、修改组织策略或放宽协议许可来规避管理员设置。手动切回仍未完成登录时，按官方流程继续核查；已经登录但后台请求失败时，避免反复登录掩盖网络问题。

## 记录最小诊断信息

记录客户端版本、发行版、桌面会话、应用内嵌 Electron/Node 版本、错误类型和时间。保留原启动器、启动参数及原 profile；修改前在本机备份启动器，确认回滚位置。不要上传原 profile、完整日志、进程环境、代理 URL、账号、令牌、Cookie、认证回调或员工会话。

检查应在应用运行的同一图形用户会话内进行。系统 D-Bus 与用户会话 D-Bus 不是一回事；终端能访问网络也不表示从桌面快捷方式启动的应用继承了相同环境。若进程环境无法读取，只能记为未知，不能认定变量不存在。

## 代理与系统证书：按证据逐项启用

本次官方 Linux `0.66.0` 的内嵌版本为 Electron `42.1.0` / Node `24.15.0`。以下开关读取于进程启动时，判断依据必须是**客户端内嵌 Node**，不是终端 `node --version` 或 PLUS CLI 使用的 Node。

| 应用进程环境变量 | 适用条件 | Node 24 分支支持起点 |
| --- | --- | --- |
| `NODE_USE_ENV_PROXY=1` | 平台已提供应用应使用的代理环境，但 Node 默认请求没有采用它 | `24.0.0` |
| `NODE_USE_SYSTEM_CA=1` | 有明确证书链验证错误，且系统信任库已经包含管理员认可的证书 | `24.6.0` |

版本与语义来自 [Node 24.15 命令行文档](https://nodejs.org/download/release/v24.15.0/docs/api/cli.html#node_use_env_proxy1)及[系统 CA 环境变量说明](https://nodejs.org/download/release/v24.15.0/docs/api/cli.html#node_use_system_ca1)。这不是所有 Node 版本或所有 Electron 网络实现的支持声明；其他分支需单独核对。

1. 确认平台代理环境已由平台或管理员正常提供。仅在 Grok Bot 专用启动器中、原应用启动命令之前加入 `export NODE_USE_ENV_PROXY=1`。保留既有 `HTTP_PROXY`、`HTTPS_PROXY`、`NO_PROXY` 及平台配置，不把实际代理地址写入公开文档，也不要全局修改所有应用的环境。
2. 正常退出后从该启动器重开同一 profile，观察实际应用错误。若没有证书错误，不必增加 CA 开关。
3. 若出现如 `UNABLE_TO_VERIFY_LEAF_SIGNATURE` 的证书验证错误，先确认系统信任来源正确，再在同一启动器加入 `export NODE_USE_SYSTEM_CA=1`，正常重开并复测。它使用系统已有信任库，仍要求证书校验通过；不会安装新 CA。系统证书缺失、过期或配置错误时，应由平台或管理员修复信任配置。
4. 如果还失败，按实际错误继续区分 DNS、代理、TLS、认证、权限和服务端问题。不要把所有 `Unavailable` 或超时都解释为账号封禁，也不要仅凭代理探针成功宣告应用修好。

这些是手动配置说明，不是可直接执行的自动修复脚本。不要盲目替换原启动器、原参数或 `--user-data-dir`；修改 shell 启动器后，应使用对应 shell 的语法检查再启动。

### 为什么额外证书变量不能作为唯一依据

Electron 的 [`nodeOptions` fuse](https://www.electronjs.org/docs/latest/tutorial/fuses#nodeoptions)可以禁用 `NODE_OPTIONS` 和 `NODE_EXTRA_CA_CERTS`。独立 Electron 探针继承了额外 CA 时，可能与正式打包应用不同。不要修改 fuse、ASAR 或安装包来使探针与应用“通过”。

本次隔离对照保留原平台代理及严格 TLS：同版官方 Electron 在 `NODE_USE_ENV_PROXY=1` 下采用了既有代理；在测试子进程中移除 `NODE_EXTRA_CA_CERTS`、模拟正式包不采用该变量的条件后，单独代理开关出现 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`；再加入 `NODE_USE_SYSTEM_CA=1`，HTTPS 和逐段返回的流式响应成功。这支持了启动配置选择，最终仍以实际客户端加载和重开结果验收。

不要设置 `NODE_TLS_REJECT_UNAUTHORIZED=0`，不要使用忽略证书错误参数，也不要删除平台原有证书变量。上述移除仅是隔离诊断对照，不是部署步骤。

## 登录持久化：修复当前桌面的安全存储

Linux 依赖桌面会话中的密钥服务。GNOME Keyring/libsecret 或 KWallet 都可能是正常选择；不需要让每台 Linux 都安装 KWallet。Electron 的 [safeStorage 文档](https://www.electronjs.org/docs/latest/api/safe-storage)列出了可选后端及 `isEncryptionAvailable()`、`getSelectedStorageBackend()` 的含义。诊断结果应在应用 `ready` 后读取，否则后端可能仍是 `unknown`。

1. 先核对重开前后是同一系统用户、同一 profile，且用户会话密钥服务已启动、可访问并解锁。优先恢复桌面本来使用的安全存储。
2. 若通过同版运行时诊断，仅读取后端名称和加密可用布尔值，不读取、解密或复制应用凭据。凭据文件只检查存在性、所有者和访问权限；文件存在本身不证明加密可用。
3. 只有确认自动选择了不可用后端，而本机另一个受支持的加密后端已经配置且可用时，才在应用原启动命令中明确选择该后端。例如已配置 KWallet 6 时可使用 `--password-store=kwallet6`。保留其余参数和原 profile。
4. 钱包创建、密码输入和解锁由用户在系统界面完成。不要使用无密码钱包、`basic_text`/`--password-store=basic` 或强制明文回退来解决持久化问题；不要复制其他用户或设备的令牌。
5. 后端切换可能使原有凭据不可解密。保留原钱包与 profile；如客户端要求认证，由用户通过官方登录流程完成，再验证持久化。不要删除旧凭据或旧钱包来“清理”。

本次环境中，自动选择 `gnome_libsecret` 时加密不可用；用户创建并解锁密码保护的 KWallet 6 后，明确选择 `kwallet6` 时加密可用，随后官方登录和重开通过。仅检查 Secret Service 是否有 owner 不足以判断 KWallet 6 是否可用；需要检查对应的用户会话服务（如 `org.kde.kwalletd6`）及实际加密可用结果。

## 手动验收与范围

完成适用修改后，逐项记录“通过 / 失败 / 未测”：

| 检查 | 通过条件 |
| --- | --- |
| 真实应用访问 | 在原生客户端核对预期账号，员工列表实际加载；只看登录成功页不算通过 |
| 安全存储 | 同一会话的受支持加密后端可用，凭据元数据符合本用户访问要求；不输出凭据内容 |
| 正常关闭重开 | 完全退出应用，再以同一启动器和 profile 打开；无需重新认证，列表再次恢复 |
| 新启动错误 | 对照该次启动时间检查连接/证书错误，避免将旧日志误作新失败 |
| 配置与回滚 | 原 profile、安装包、平台代理和策略保持完整，启动器备份可定位 |

2026-10-06 的实际通过范围：官方 Linux Grok Bot `0.66.0`，正确账号及员工列表加载、加密持久化、**当前桌面会话且钱包已解锁条件下**正常关闭重开自动恢复。未验证整机重启、桌面注销后的解锁或无人值守钱包解锁；不能由应用重开通过推断这些也通过。

这次验收未派发员工业务任务，不等于公开 PLUS 精确发行构建已完成 `0.66.0` 全部真实验证。PLUS 路由、模型请求、历史、重连、员工归属、profile 隔离和调度应按[兼容性文档](COMPATIBILITY.md)另行验证；需要消息往返时使用获准的独立测试会话，避免重复派单。

## 回滚与后续更新

1. 正常退出应用，用修改前的本机备份恢复专用启动器；或者精确撤回本次新增的环境变量和后端参数，保留原有配置。
2. 继续使用原 profile 和原系统用户启动。不要删除钱包、凭据、缓存、身份文件或员工云电脑来回滚启动参数。
3. 如果回滚后密钥后端不可用，保留数据并修复该桌面会话的密钥服务；需要认证时由用户正常登录。不要把令牌迁移作为恢复步骤。
4. 官方更新后重新确认实际客户端版本、内嵌运行时、启动入口和全部适用验收项。旧启动器可能不再是桌面快捷方式所用入口，旧成功记录也不能证明新版本正常。

Windows 不应照搬本指南的 Linux shell、D-Bus 或 KWallet 步骤。其安全存储使用不同机制，代理和系统信任也需在实际 Windows 应用运行时独立验证；本指南没有提供 Windows 修复验收结论。
