# 员工连续性：四层状态与迁移检查

本文整理实际迁移中发现的边界，不提供一键修改账号的脚本。

## 四层状态

| 层 | 需要核对 | 常见误判 |
| --- | --- | --- |
| 身份 | 原 agent ID、归属与执行位置 | 新建同名 Bot 就算恢复原员工 |
| 历史 | 平台可见聊天、本地会话、文件和记忆 | 复制可见文本就等于恢复隐藏 checkpoint |
| 路由 | 客户端进程中的 roster/harness、Box 收件与平台会话 | 服务端已改配置，客户端一定会刷新 |
| 调度 | 每项任务唯一的执行方、启停状态、时间区、执行收据 | 两边同时开着能增加可靠性 |

更换推理供应商只改变其中一部分。客户端仍可能把消息送到平台；一个未刷新的客户端进程也可能继续使用旧路由。

## 建议顺序

1. 只读盘点原身份、当前路由、可见历史和任务。记录每个来源及采集时间，备份本地状态。
2. 保留原 ID。确认本地已有正确资料和会话；不要为了“恢复”批量创建同名身份。
3. 对分叉的历史做带来源和时间的只读交接。旧消息作为历史材料，不能当作重新授权或新任务自动执行。
4. 单独验证客户端到 Box 的收件路径，必要时完整重启客户端后重新获取 roster。
5. 将每项定时任务明确交给一个调度方，核对原启停状态、时区和触发类型。停机前时间槽不补跑。
6. 用无副作用消息完成真实客户端往返，再单独验收定时任务；保留时间与脱敏收据。

## 证据的含义

- HTTP 200 只能证明某次接口调用成功，不能证明用户正在看的会话收到了它。
- 可见历史归档和本地交接能够补充上下文，但不恢复平台隐藏的内部状态。
- 模型说“已经恢复”不是配置、路由或任务状态的证据。
- 原身份、原文件、可见历史和隐藏平台状态应分别描述保留范围，不能统称“无损”。
