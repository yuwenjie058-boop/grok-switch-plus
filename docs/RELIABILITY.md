# 账本可靠性：保证、测试与限制

alpha.2 对 alpha.1 的账本写入进行了补强。默认仍关闭上下文裁剪。

## 提交步骤

1. 请求加载账本快照并计算候选裁剪。
2. 保存时以独占目录锁串行化合作写入方；被占用则放弃本次新裁剪，不抢锁。
3. 在锁内重读账本。若已改变或无法解析，不覆盖它。
4. 使用独占创建的随机临时文件，写入并 `fsync` 后重命名。
5. Linux 上继续刷新父目录，确认目录项；Windows 不宣称同等级的断电持久性。
6. 只返回仍有账本记录的新裁剪形态；同批次被容量淘汰的候选还原为原输出。

文件写入、刷盘或重命名之前失败：新裁剪还原，已有可恢复记录可继续重放。重命名完成后若目录刷新失败，文件可能已经可见，因此返回 `GROK_SWITCH_COMPACT_COMMIT_UNCERTAIN`，阻止该次供应商请求，避免悄悄发送与下次重放不同的形态。

## 并发和容量边界

目标部署是**一个活跃宿主进程**。保存锁与快照比较用于防止合作进程覆盖彼此记录，不把本地文件系统变成分布式数据库。它不保证多机共享目录、外部不遵守锁的写入方、网络文件系统或损坏存储上的一致性。

锁竞争时放弃的新裁剪会保留完整证据，但可能损失前缀缓存命中；不能宣传为任意并发下字节永远不变。正常单进程同步执行不会在此读写段内交错。

`ledgerMaxEntries` 是容量上限。记录被淘汰、账本丢失、缓存恢复失败或手动修改均可能改变重放形态。alpha.2 修复了“同一次请求已经淘汰记录，却仍返回新裁剪结果”的问题，未承诺有限账本可以无限期保留所有历史。

## 异常恢复

- `ledgerWriteFailed`：检查存储权限、容量、账本 JSON 和竞争写入。不要用删除账本来隐藏错误。
- `capacityHeld`：本次部分新裁剪因容量没有保留记录，已返回原输出；结合活跃会话和磁盘预算评估容量。
- `GROK_SWITCH_COMPACT_COMMIT_UNCERTAIN`：先检查存储与账本，不要自动反复发请求。
- 遗留 `ctx-compact-ledger.json.lock`：只有停止全部写入方并确认无活跃提交后，才可备份运行目录并人工移除这个空锁目录。程序不会凭时间推断锁已失效。
- 损坏账本：停止写入并保留文件，优先从可信备份恢复；恢复不了时应把新账本视为一次上下文/缓存重置。

## 验证覆盖

`tests/ctx-ledger-durability.test.mjs` 覆盖刷盘失败、锁占用、另一个进程在快照后提交、损坏文件、容量淘汰以及 Linux 目录刷盘不确定性。runtime 测试验证“不确定提交”不会被吞掉后继续调用供应商。现有缓存原文写入失败与恢复测试继续运行。

这是故障注入和真实文件读写测试，不是断电实验，也不是任意文件系统的持久性认证。测试不能消除硬件、文件系统及操作系统本身的限制。
